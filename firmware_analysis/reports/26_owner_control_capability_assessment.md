# RBRE960/RBSE960 Owner-Control Capability Assessment (stock firmware)

**Goal:** maximum owner control via a separate out-of-band management host (a VM on dedicated hardware) that drives the
**unmodified** Orbi over authenticated SSH/ubus. No flashing, read-only research first.

**Evidence base:** extracted firmware (`rbre_7215`) + live-master runtime (`ip a`, `ubus -v list`,
process/port dumps). Labels: VERIFIED / STRONGLY INDICATED / HYPOTHESIS / UNKNOWN / RULED OUT.
Classes: NATIVE / ROOT-AVAILABLE / HIDDEN / EXTENSIBLE / EXTERNAL / HARDWARE-DEPENDENT / UNSUPPORTED / UNKNOWN.

---

## A. Architecture verdict (APPROVED)

The "management host out of the forwarding path, Orbi stays authoritative" design is the #1 principle. The Orbi already runs all routing/DHCP/DNS/mesh locally; the
management host only *observes and proposes*. If the management host dies, the network is unaffected.

Consequence for rollback (important): because the portal is out-of-path, the rollback timer
**must run on the router itself** (native uci apply/confirm), not in the VM - which is exactly
what §B establishes.

---

## B. Configuration safety / rollback mechanism

### B1. What implements `uci apply/confirm/rollback`
- No `/usr/lib/rpcd/uci.so`; the `uci` object is **built into `/sbin/rpcd`**. That binary
  contains `rollback` + `uloop_timeout_set/cancel/remaining` - the genuine transactional
  apply-with-timer. (STRONGLY INDICATED, static; VERIFY with the safe test in §B4.)
- Flow (stock OpenWrt semantics, to be confirmed on-box): `apply {rollback:true,timeout:N}`
  commits the staged delta to `/etc/config`, reloads affected services, and arms a timer;
  `confirm` cancels it; on timeout the pre-apply snapshot is restored and services reloaded.

### B2. Coverage - what rollback does and does NOT protect
| Subsystem | UCI-managed? | Covered by uci rollback? | Notes |
|---|---|---|---|
| `network`, `dhcp`, `wireless`, `system`, `dropbear`, `upnpd`, `repacd`, `hyd`, `wsplcd` | yes (`/etc/config/*`) | **Yes** (for the parts genuinely read from UCI) | VERIFIED these files exist |
| **Firewall** | **No** - `firewall_script.sh` + iptables; no `/etc/config/firewall`, `fw3` absent | **No** | A bad firewall change is **not** auto-reverted. Must be handled with its own backup/restore + timer. (VERIFIED) |
| **NVRAM/ACOS settings** | partially mirrored into UCI by `configd` | **No / unreliable** | `configd` + `libntgrnvram` can regenerate `/etc/config` from NVRAM; a `uci set` to an NVRAM-backed option may be overwritten at regen/boot. (STRONGLY INDICATED) |
| Wireless driven by `nvram_wifi` / repacd | generated at runtime | **Partial** | live `network`/`wireless` is augmented by repacd/hyd/nvram beyond the image defaults |

### B3. Reboot behavior (critical caveat)
The rollback snapshot and timer live in **tmpfs/uloop (RAM)**. If the router **reboots before
`confirm`**, the timer is lost and the **applied (possibly bad) config persists** with no
auto-revert. (STRONGLY INDICATED by design.) => Never rely on uci-rollback alone across a
reboot; always pair with an off-box `/etc/config` + nvram backup (Layer 3).

### B4. Required safe verification test (first intentional change; needs backup + approval)
Before ANY config-writing feature is built:
1. Off-box backup: `scp` a tarball of `/etc/config`, `nvram show`/`fnvram`, and
   `firewall_script.sh` state to the workstation and off-box storage.
2. On the router, apply a **benign, reversible** change (e.g. a dummy uci config option) via
   `ubus call uci apply '{"rollback":true,"timeout":90}'` and **do not** confirm.
3. Observe: does it auto-revert at ~90s? Does `uci changes`/service state return to baseline?
4. Repeat with `confirm` to see persistence. Reboot-during-window test only on a scheduled,
   recoverable window.
This proves the timer semantics on *this* firmware rather than assuming OpenWrt behavior.

**Acceptance gate honored:** no portal write-path until B4 passes.

## C. VLAN feasibility matrix

Headline (VERIFIED from live `ip a`): **the mesh backhaul is already an 802.1Q trunk.**
`ath11.4093->br-guest`, `ath11.4094->br-lan`, `ath2.4093/.4094`, and wired `eth0..3.4093` show
the firmware already tags guest=4093 / lan=4094 and carries them over the wireless backhaul.

| Capability | Class | Evidence / caveat |
|---|---|---|
| 802.1Q tagging on wired ports | NATIVE | `eth0.4093@eth0` live; `swconfig`,`ssdk_sh`,`bridge` present |
| Tagged VLANs across wireless backhaul | NATIVE (today, for 4093/4094) | live `athX.409x` subifs bridged; mechanism = QCA SON/repacd + hyd 1905 |
| **Additional SSID->VLAN** (IoT/Servers/Mgmt) | HIDDEN / EXTENSIBLE | `hostapd` has `dynamic_vlan`/`vlan_bridge`/`vlan_file`/`per_sta_vif`; but VAP/bridge/tag config is generated by NETGEAR nvram_wifi+repacd - adding a VAP means fighting the config layer AND mirroring on satellites via SON |
| VLAN-aware bridge / filtering | HIDDEN | kernel bridge + `bridge` util present; current design uses separate br-lan/br-guest, not a single vlan-aware bridge |
| Inter-VLAN routing | ROOT-AVAILABLE | `ip`/kernel routing; but NSS offload (`nsstbl` qdisc) means HW-accel paths need care |
| Per-VLAN DHCP scope | ROOT-AVAILABLE | `dnsmasq` multi-instance; add interface + dhcp section |
| Per-VLAN DNS | ROOT-AVAILABLE | dnsmasq views/instances |
| Inter-VLAN firewall / isolation | ROOT-AVAILABLE (NOT uci-rollback-protected) | NETGEAR iptables script; must manage + back up separately (§B2) |
| IGMP snooping / multicast per VLAN | NATIVE/HIDDEN | `igmpproxy` present; bridge mcast snooping |
| QoS / rate-limit per VLAN | ROOT-AVAILABLE | `tc` present; interacts with NSS offload |
| IPv6 per VLAN | ROOT-AVAILABLE/UNKNOWN | master uses dnsmasq (odhcpd absent); v6 already on br-lan/br-guest |
| **Satellite mirroring of new VLANs** | UNKNOWN (key risk) | new VLANs must be instantiated on RBSE too; only the SON/repacd push is supported, and it syncs vendor-defined params - custom VAPs may not propagate |
| Hardware NSS offload correctness w/ custom VLANs | UNKNOWN | custom tags may fall back to slow path or break accel |

**VLAN bottom line:** technically the backhaul trunk + hostapd + switch all support more VLANs,
so this is **not blocked by hardware**. The real obstacles are (1) the NETGEAR nvram/repacd
config layer that owns VAP/bridge generation, (2) propagating new VLANs onto the satellites
through a sync path built only for vendor-defined networks, and (3) NSS offload behavior.
**Recommendation:** treat deep SSID-VLAN segmentation as *plausible but high-risk on the Orbi*;
if a clean 5-VLAN design is a hard requirement, a VLAN-capable managed switch + (optionally)
dedicated APs behind the Orbi is the low-risk path, with the Orbi kept for its mesh coverage.

## E. Recommended build order (read-only -> low-risk writes)

1. **Inventory + read-only dashboard** (zero device risk): SSH-collect ubus/iface/wireless/
   client/satellite/traffic data into the VM; visualize topology, signal, backhaul, clients.
2. **Backup/audit service**: scheduled off-box export of `/etc/config` + nvram + firewall state,
   versioned in Postgres/git, off-box copies. (read-only on router)
3. **Verify rollback (§B4)** - first intentional write, with full backup and owner approval.
4. Only then: scoped, audited **write** operations (DNS/DHCP first - uci-covered; firewall
   last - separate safety), each through create-backup->plan->arm-rollback->apply->health-check->
   confirm/revert.
5. VLAN work: prototype one extra VLAN end-to-end incl. a satellite before committing to the
   5-VLAN design; decide Orbi-native vs managed-switch based on the satellite-propagation test.

## F. Open questions needing operator input / live verification
- **Management-host networking:** is the host bridge VLAN-aware, which physical NIC faces the Orbi, and is a
  managed switch already present? This decides Orbi-native VLANs vs. added switch (§C bottom line).
- Live-verify: rpcd rollback semantics (§B4), which `/etc/config` options are NVRAM-backed
  (configd overwrite risk), and whether a new VLAN propagates to a satellite via SON.
