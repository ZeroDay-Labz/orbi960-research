All 128 slots returned VID 0 and empty port membership through the
swconfig interface.

Important interpretation note:

- This proves only that the stock vendor firmware does not program VLAN
  slots through the legacy swconfig surface.
- QCA HPPE is managed by the SSDK/NSS stack in practice. Hardware VLAN
  state may be programmed through `ssdk_sh` or NSS-internal APIs and
  not be visible through `swconfig vlan N get vid/ports`.
- We did NOT run `ssdk_sh` queries or other vendor-native queries that
  would surface hardware-programmed VLAN state not visible to swconfig.

Therefore: "swconfig view shows all 128 slots unprogrammed" is a
SUPPORTED claim; "no VLAN state is programmed in the HPPE" is NOT.

- The generated configs confirm the UCI→HYD translator is producing
  only the reserved-VLAN (4093/4094) wiring that the stock mesh
  requires.
- `ManagedInterfacesList` on br-lan labels backhaul interfaces
  `ath11.4094@wifi1&lan:WLAN_VLAN` and `ath2.4094@wifi2&lan:WLAN_VLAN`
  — the `WLAN_VLAN` role is how HYD tags a VLAN-carrying wireless
  sub-interface. The guest config does the same with .4093.
- The MultiAP VLAN separation knobs are all 0 in both generated files
  — consistent with the UCI dump. The feature is schema-defined but
  NOT ACTIVE.
- VlanIds=eth1.4094,eth0.4093 is identical across both generated
  files — the global VLAN list HYD knows about.

Therefore:

- The HYD stack has a schema for Multi-AP SSID-to-VLAN separation
  (NumberOfVLANSupported/Map2TrafficSepEnabled/VlanIDNw{Primary,One,
  Two,Three}/Map8021QPCP), confirmed by both the UCI schema and by the
  generated conf files that include these keys.
- That schema is currently inactive. All related values are 0.
- The UCI-to-generated-conf translator code (likely in
  /lib/wifi/*.sh or NETGEAR vendor scripts; not inspected this turn)
  must be reverse-engineered before any owner-added SSID-to-VLAN
  wiring can be driven through this surface.

  hyfi_get_iface_vlanids()    { # L85
      IFACE_VLANIDS=""

Reverse-engineered UCI→HYD VLAN translator (CONFIRMED):

  UCI /etc/config/hyd:                    Generated hyd conf:
  --------------------------------        -------------------------------
  @Vlanid[N].ifname = <iface>             VlanIds = <iface1>.<vid1>,
  @Vlanid[N].vid    = <vid>                         <iface2>.<vid2>, ...
  config.SwitchLanVid = <lan_vid>         SwitchLanVid = <lan_vid>
                                           SwitchCpuPort = <from switch_vlan
                                                            section in
                                                            /etc/config/network
                                                            matching lan_vid>

This matches the live example byte-for-byte:
  @Vlanid[0] eth1:4094 + @Vlanid[1] eth0:4093 + SwitchLanVid=1
  → VlanIds=eth1.4094,eth0.4093 + SwitchLanVid=1

Implication for the owner-agent:

- To introduce an owner VLAN at the HYD layer, one would add a new
  `config Vlanid` section to `/etc/config/hyd` with `ifname` and `vid`,
  then restart hyd. No MULTI-AP SSID-to-VLAN wiring is required for
  this ifname.vid list; those two mechanisms are independent.
- MAP/Multi-AP SSID-to-VLAN wiring (the NumberOfVLANSupported,
  Map2TrafficSepEnabled, VlanIDNwPrimary/One/Two/Three knobs) is a
  SEPARATE subsystem and is currently disabled (all zeros). That is
  the part of the capability matrix that remains deferred, not the
  `@Vlanid[*]` → VlanIds path.
- This clarifies the Phase-B investigation scope: the UCI→HYD
  translator for ifname.vid is NOW UNDERSTOOD; the SSID-to-VLAN MAP
  path is NOT (requires hostapd + MAP + repacd integration study).

All have `vlan protocol 802.1Q id <vid> <REORDER_HDR>` — plain Linux

This is the stock vendor mesh/guest pattern: wired ports carry VLAN
4093 (guest) when a cable is up; wireless `ath11.*` and `ath2.*`
carry VLANs 4093 (guest) and 4094 (mesh backhaul) on the two backhaul-
capable radios.

Confirms: the owner-agent's `vlan_create` would produce an identical
structural result (software 802.1Q sub-interface + bridge_slave of a
chosen bridge), using the vendor's own precedent.
